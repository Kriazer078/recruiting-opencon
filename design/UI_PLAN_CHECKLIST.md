# План полного интерфейса Open Consulting

Дата: 5 октября 2026 года.

Основа: [ТЗ версии 1.1](../TZ_OPEN_CONSULTING_V1_1.md). Пользователь выбрал последовательность: сначала полный интерфейс и внешний вид, затем реализация логики и интеграций.

Статус: план работ предложен; дизайн и спорные требования ещё не утверждены. Старые прототипы служат историей поиска, готовые решения из них автоматически не переносятся.

## Цель этапа интерфейса

Получить единый связанный прототип публичного сайта и четырёх кабинетов. Он должен показывать весь путь от первого посещения до подтверждения отелем и сопровождения выезда, включая заполнение, ожидание, отказ и восстановление после ошибки.

В прототипе используются демонстрационные данные. Статусы, оплаты, переводы и проверки моделируются и явно обозначаются в режиме демонстрации. После этого подключаются сервер и внешние сервисы.

Правила переходов, ограничения и доступ по ролям проектируются сейчас: от них зависит состав интерфейса. Реальная проверка этих правил на сервере относится к следующему этапу разработки.

## Порядок работы

| Этап | Что делаем | Результат |
| --- | --- | --- |
| 1. Карта продукта | Роли, навигация, основные сценарии, перечень экранов и состояний | Согласованная структура полного интерфейса |
| 2. Визуальное направление | Конкретные референсы, композиция, типографика, фирменные материалы | Одна выбранная система оформления |
| 3. Первые опорные экраны | Главная, кабинет кандидата, запись презентации | Понятно, как выглядят публичная часть, рабочие экраны и видео |
| 4. Общие компоненты | Формы, кнопки, карточки, таблицы, статусы, уведомления и окна | Повторяемый набор элементов для всех ролей |
| 5. Путь кандидата | Регистрация → анкета → публикация → предложения → интервью → выбор | Полностью проходимый сценарий кандидата |
| 6. Путь отеля | Проверка компании → вакансия → кандидат → интервью → подтверждение | Полностью проходимый сценарий работодателя |
| 7. Оператор и партнёр | Проверки, модерация, сопровождение, контент и собственные кандидаты | Два кабинета с разными правами |
| 8. Общие рабочие процессы | Комната интервью, оплата, уведомления, визовый трек | Связь между действиями всех участников |
| 9. Адаптация и языки | Телефон, компьютер, длинные тексты, четыре языка | Согласованное поведение интерфейса на устройствах |
| 10. Сборка и передача | Переходы, состояния, описание поведения компонентов | Готовый прототип и спецификация для реализации |

Очередность показывает последовательность проектирования. Полный календарь и сроки здесь не назначены. Карта экранов и сценариев уточняется по мере согласования ТЗ.

### Основные цепочки

**Кандидат:** главная → вход → лицо → анкета → фото → презентация → документы → оплата/код → модерация → опубликована → вакансии/предложения → интервью → выбор одного отеля → подтверждение → сопровождение.

**Отель:** главная → регистрация → сведения и документы компании → проверка → вакансия → модерация → кандидаты/отклики → предложение → назначение интервью → интервью → подтверждение или повтор → сопровождение.

**Оператор:** очередь проверок → карточка лица/компании/анкеты → решение и причина → расписание и перевод → документы и статусы → контроль подтверждения и сопровождения.

**Партнёр:** свои кандидаты → регистрация и источник → материалы и статусы → свои собеседования → перевод → собственные отчёты.

Порядок окончательного выбора и подтверждения требует уточнения по ТЗ. В прототипе обозначать выбранное временное решение.

## 6. Состояния, которые необходимо показать

- [ ] У кандидата не завершено заполнение или не пройдена проверка.
- [ ] Оператор вернул анкету/документ с конкретным замечанием.
- [ ] Все три слота заняты; четвертое одобрение недоступно с объяснением.
- [ ] Предложение истекло; слот освободился.
- [ ] Один отель уже выбран; показаны последствия для других предложений.
- [ ] Интервью назначается менее чем за пять часов; видна причина ограничения.
- [ ] Изменение режима позднее установленного срока недоступно.
- [ ] Закончился оплаченный период; кабинет и файлы сохраняются.
- [ ] Нет подходящих вакансий, кандидатов, новостей или интервью.
- [ ] Нет прав на файл или чужую запись.
- [ ] Сбой платежа, проверки, загрузки, видеосвязи либо перевода.

Поведение при спорном сроке или событии обозначается как предположение и включается в список решений заказчика.

## 8. Когда полный интерфейс можно считать готовым

- [ ] У каждой функции согласованного объёма ТЗ есть экран/состояние или указание, где она отображается.
- [ ] Можно пройти главные сценарии четырёх ролей в связанном прототипе.
- [ ] Понятны начало, следующий шаг и итог каждого действия.
- [ ] Продуманы успешные, пустые, ожидающие, ошибочные и недоступные состояния.
- [ ] Все группы экранов используют общие компоненты и визуальные правила.
- [ ] Проработаны телефон и компьютер, перечислены различия приложений.
- [ ] Ограничения трёх слотов, одного места и пяти часов объясняются в интерфейсе.
- [ ] Права на документы и записи отражают согласованную матрицу доступа.
- [ ] Спорные требования, суммы и тексты выделены; утверждённые решения имеют источник.
- [ ] Составлена спецификация компонентов, переходов, адаптации и анимации для разработчика.
- [ ] Пользователь рассмотрел полный результат и зафиксировал правки.

После этого переходить к базе данных, серверным правилам, доступу по ролям, реальным платежам, проверке лица, ЭЦП/SMS, видео, переводам и уведомлениям. Для подключения каждой функции использовать уже спроектированные состояния интерфейса.

## Первая конкретная задача

**Карта экранов и переходов → схемы главной, кабинета кандидата и записи презентации → выбранное визуальное оформление этих экранов.**

Следующий артефакт: карта продукта с идентификаторами экранов, связями, ролями и открытыми вопросами. После её составления — первый визуальный результат главной на компьютере и телефоне.
